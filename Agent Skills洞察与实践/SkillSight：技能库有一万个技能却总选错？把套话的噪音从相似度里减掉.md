# 技能库里有一万个技能，你的Agent却总选错

---

# 场景：一次失败的技能调用

Agent平台接入了上千个技能。用户说："帮我把上周的销售数据做成图表发到飞书群。"

检索器跑了一轮稠密匹配，返回Top-5。排第一的叫"数据可视化工具"，描述是"支持对结构化数据进行图表生成，输出PNG/SVG格式，适用于数据分析场景"。排第二的叫"飞书消息推送"。

Agent选了第一个。失败了。它真正需要的是一个能"读数据库→生成图表→推送到飞书"的端到端技能，不是一个通用的图表渲染器。

检索器的语义理解没毛病。那问题在哪？

---

# 根因：技能文档长得太像了

随便打开一个技能库，你会发现大量文档共享着几乎一模一样的描述模板。

"支持对××数据进行××处理"、"适用于××场景"、"基于××模型实现××功能"——每个技能都这么写。学术上管这个叫**共享描述背景**（Shared Descriptive Background）：技能文档互相之间长得太像了。

稠密检索器的工作方式是算查询和文档的整体语义相似度。当一个技能文档带了大量套话，它的得分里就混进了一个跟实际能力无关的"背景分"。一个完全不匹配的技能，可能因为模板写得好，得分比真正对的技能还高。

论文的作者把这个现象拆开来，算了三笔账。

**第一笔：排序。** 技能检索里，排在正确答案前面的无关文档比例，显著高于传统文本检索。套话在把不相干的技能往上推。

**第二笔：Token。** 出现频率越高的词，对区分技能的贡献越小。统计上，高频通用词的"命中率"集中在零附近——它们编码的是模板结构，不是能力差异。

**第三笔：能量。** 如果把所有通用Token的方向聚成一个"背景子空间"，技能文档在这个子空间上的投影能量系统性地高于查询。说明技能文档跟套话的耦合程度远高于用户查询。稠密得分可以正交拆成两项：一项来自背景对齐，一项来自残余对齐。文档背景能量越高，真正跟能力有关的信号就越容易被淹没。

一句话：**稠密检索的相似度算分，被技能文档之间的共享描述污染了。** 这不是检索器的bug，而是技能文档这个文本类型的结构性特征。现有的方法——不管是去掉通用嵌入方向，还是做混合检索——都没把这件事单独拎出来处理。

---

# 解法：两条通道，各治一个病根

既然问题出在"相似度里混进了背景噪音"，那解法就该是把噪音减掉。但减噪音不够——那些真正能区分技能的细粒度词汇（操作名、实体名、参数约束），在稠密嵌入里被平滑掉了，也得捡回来。

SkillSight做了两条通道：**SBC负责减去语义背景噪音，LEC负责找回词汇区分信号。** 都不需要训练，不需要部署重排序模型。

---

# SBC：把套话的分量从相似度里减掉

这个通道的逻辑是：既然通用Token构成了一个"背景子空间"，那把查询和文档的嵌入向量里属于背景的那部分成分抽掉就行了。

**怎么做。** 分三步。

1. 用IDF找出所有"通用Token"——在大量技能文档里反复出现的词，就是套话的词汇基础。用大津法自动找一个IDF分割点，免去手调阈值。
2. 每个通用Token对应一堆包含它的文档，把这些文档的嵌入向量取平均，就得到这个通用Token在嵌入空间中的"语义方向"。把所有通用Token的方向向量摞成一个矩阵，做SVD，取前r个左奇异向量，构成背景子空间的正交基。
3. 对任意查询和文档嵌入，投影到背景子空间的正交补空间上。投影后的向量再算内积，就是去掉背景噪音之后的相似度。

本质上是在做什么？原始稠密得分等于"背景对齐"加"残余对齐"。SBC直接丢了背景对齐那一项，只留残余对齐。

**一个关键细节：投影之后不重新归一化。** 常规的表示空间校正方法在投影后会把向量重新拉到单位长度。SBC不这样做。原因很直接：一个套话写得特别多的技能文档，投影之后剩下的有效语义向量会变短——归一化等于把这个"短"给抹平了，反而人为抬高了它的排名。不归一化，向量长度天然记录了"剥离背景后还剩多少真正跟能力相关的东西"。文档越"虚"，得分越低，自动排序。

**开销。** SBC的工作全在离线完成——IDF统计、Token筛选、SVD、文档投影——都在索引构建阶段算好。在线只需要对查询向量做一次投影，几乎不增加延迟。

---

# LEC：把词汇层面的区分信息捡回来

SBC从语义空间角度解决了背景噪音。但还有个问题：稠密嵌入天然倾向于"理解大意"，对精确的词汇匹配不那么敏感。比如技能描述里的具体操作名、实体名、参数约束——这些词在嵌入里经常被平滑成"差不多"的语义，丢了区分力。

LEC要做的事就是把这些细粒度的区分信号捞回来。

传统的IDF加权能做一部分：稀有词权重高，常见词权重低。但在技能检索场景里不够用。一个词，IDF不一定低，但仍然出现在了30%、50%的技能文档里——它不算通用词，区分力却有限。

**LEC在IDF之上加了一层：文档普遍性折扣。** 对查询里的每个非通用词，看它出现在多少比例的技能文档里。如果90%的文档都有它，大幅压低权重。如果只有1%的文档有它，几乎保留全部权重。β是校准强度，控制折扣的力度——β=0就退化成标准IDF。

有了权重之后，LEC算的不是传统的词袋匹配，而是"加权覆盖率"：查询里那些有区分力的词，有多少被候选文档精确命中了。分子分母一除，结果是个零到一的值。只用精确匹配，不加软匹配——因为语义相近的情况稠密已经覆盖了，LEC就管精确命中。

---

# 两条通道怎么合

语义得分是嵌入内积，词汇得分是覆盖率比值，量纲不一样。SkillSight的做法是：先在候选集内各做z-score归一化，再加和。

候选集内归一化的好处：不同查询的得分分布差异很大，有的整体偏高、有的偏低，候选集内归一化抹平了这个查询级别的偏移。

词汇通道取非负截断：低于候选集均值的文档不给正向修正，也不反扣。SBC的语义得分扛主排序，LEC只负责把词汇匹配确实好的文档往上提一档。一种很干净的退化行为：如果所有候选文档在词汇上表现完全一样，修正项归零，排序完全依赖SBC。

**性能。** 离线阶段的工作都在索引构建时完成。在线只有查询投影、候选集词汇得分计算和z-score归一化，没有任何神经网络推理。做个对比：Dense+Reranker要对每个候选做一次完整交叉编码，300个候选就是300次自注意力。SkillSight快677到1248倍。

# 实验：几个关键数字

**离线检索。** SRA-Bench上Recall@10从66.02推到**86.23**，涨了20.21个百分点。更大的SkillBench-Supp（约77k候选）上同样稳定涨点。

**端到端。** Llama-3.1-8B、GPT-5.4-mini、Qwen3-4B三个模型上，SkillSight全部拿到非预言机方法里最好的Overall成绩，分别比LLM Selection高出**4.97、1.84、4.28**个百分点。模型越弱、任务越难，提升越明显。

**消融。** 单独给Dense加LEC，Recall@10从66.02跳到79.76，纯靠词汇层面的精确匹配就补了一块。单独给BM25加SBC，召回率涨了11.90。两个通道各自管用，互补。

# 这对你的Agent平台意味着什么

检索层是Skill飞轮转起来的第一步。技能被正确选中、正确调用，后面的评测、诊断、优化才有意义。这一步被套话匹配带偏了，整个闭环都是空中楼阁。

SkillSight给的路线很轻量：不训练、不加模型、不改检索架构。在现有稠密检索之上做两道校准——语义去背景，词汇补细粒度。任何一个Agent平台的检索栈都能直接装。
