# 你的Agent技能库安全吗？不是问Prompt注入：是整个生命周期

---

# 一个只盯着一扇窗的安保

Agent技能（Skill）已经是基础设施了。OpenAI、Anthropic、Google都在推可复用的技能生态：把工具调用、执行策略、权限声明打包成一个标准化工件，Agent按需检索和调用。这跟之前的Agent开发模式有本质不同——不是手写Prompt告诉模型该怎么做，而是让模型去检索并调用外部传来的可执行工件。Snyk去年扫了近4000个公开技能，36.82%至少含一个安全问题，13.4%是Critical级漏洞。安全和功能之间的距离，在技能生态里被拉得比以往任何时候都近。

但安全社区一直盯着一扇窗。Prompt注入：用户输入里夹带恶意指令、工具返回结果里嵌隐藏提示。这些研究够多了。问题是，一个Skill从被人写出来到被Agent执行，中间跨了六七道门，每道门有自己独立的信任假设和攻击面。Prompt注入只是最后一道门的锁。

一篇Google的安全论文对此做了系统拆解：《Agent Skill Security: Threat Models, Attacks, Defenses, and Evaluation》。它提了一个技能生命周期的威胁分类法，搭了一套可复现的评估框架SkillSec-Eval，在327个真实技能上把每道门的攻防都测了一遍。

核心结论就一句：看住最后一道门不够。**技能安全风险分布在完整生命周期的多个阶段，不只在执行期。**

---

# 六道门，六种信任假设

论文把技能的生命周期拆成六个阶段。每个阶段一种信任假设，攻击者打破它，后续的所有环节就在错误前提下运转。

**第一道门：创作（Authoring）。** 开发者或自动化系统编写技能：工作流定义、语义描述、执行策略、权限声明。信任假设是"写进规约里的东西跟代码跑出来的行为一致"。打破这个假设的方式很多：隐藏不一致的指令、写虚假能力描述、申报超出实际需要的权限。权限膨胀（Permission Inflation）是这一层最典型的攻击：广告功能只是"查询数据库"，背地里申请了Shell执行和网络出站权限。

**第二道门：存储（Storage）。** 技能发布到仓库，等Agent来检索。信任假设是"仓库里的东西是没被篡改过的原件"。攻击分结构层和语义层两路。结构层：去签名、篡改Payload、版本回滚到一个有漏洞但签名有效的旧版本。语义层：权限申报跟广告不符、描述写得很正经但工作流里藏了恶意指令、在元数据里夹带Prompt注入载荷。传统软件供应链安全管得住结构层——SHA256校验、数字签名——但对语义层完全瞎。一个Skill可以在签名有效、Hash匹配的情况下，描述写的是"数据查询"，工作流里跑的是"数据查询+外发"。规则引擎看不出来。

**第三道门：检索（Retrieval）。** Agent根据用户请求去仓库搜匹配的技能。信任假设是"检索器返回的候选，既语义相关又值得信任"。攻击者做的事可以称为Agentic SEO：关键词堆砌抬高嵌入相似度、语义伪装把恶意行为藏在通顺描述里、Sybil攻击克隆几十个近似技能霸占检索窗口、触发器下毒让特定查询命中恶意技能。这四招本质上都是利用嵌入空间的特性——稠密检索算的是整体语义相似度，不区分"能力描述"和"恶意载荷"，只要字面上足够接近目标领域的语义分布，恶意技能就能混进候选集。

**第四道门：选择/规划（Selection/Planning）。** Planner从检索器吐出的Top-K候选中挑一个执行。它几乎只看元数据，不看工作流代码。信任假设是"元数据真实反映了技能行为"。攻击空间：虚假推荐标记、能力误导描述、权限申报低于实际需要、在描述里嵌入自然语言指令诱导选择。

**第五道门：执行（Execution）。** Skill的实际工作流跑起来，调用工具、产生副作用。信任假设是"被选中的工作流只在授权范围内操作"。攻击类型：把两个单独无害的技能组合成恶意链条、越权调用工具、跨步骤信息泄露、数据外泄绕过监控。执行安全不是单步检查，是多步工作流中的信息流问题。

**第六道门：进化（Evolution）。** 技能被发布后不是死的：会更新版本、改依赖、增删权限、修订元数据。信任假设是"更新之后的技能保留了之前积累的可信度"。现实中：新版本悄悄加网络权限、在正常更新里夹带恶意指令、替换底层工具为更危险的选择、依赖被污染、发布者凭证被盗。**没有谁每次更新都重新审计，但信任旧版本的惯性就是攻击面。**

# SkillSec-Eval：逐道门测攻防

光列威胁分类不解决问题。论文搭了一套评估框架SkillSec-Eval，每道门前都放攻仿对，量化衡量防线有效性。

数据集：327个真实技能，来自SkillMCP公开仓库，分成15个能力集群：CRM自动化、身份访问管理、容器安全、数据库优化、DevOps等。每个集群塞进20到25个语义相近的技能，制造稠密检索邻域。攻击样本在每个生命周期边界独立生成，覆盖六类攻法。五道防线各测各的。

**仓库准入。** 三种配置。纯规则防线，签名校验、Hash对比、正则检测不安全代码模式，把恶意准入率压到52.9%。失败近半：规则能揪结构畸形，对"描述滴水不漏、行为偷偷摸摸"的攻击没分辨力。换成纯语义防线，LLM审描述与行为的一致性，准入率降到42.9%，但误杀率飙到20%。两套串联，规则先过、LLM后验，恶意准入率压到7.9%。代价是误杀率仍是20%：LLM语义线拦截了93%的语义攻击，同时误判了两个合法Skill。论文的措辞很清醒：LLM语义验证必要，但"引入开发者摩擦"，且在零日逃逸面前仍有缺口。

**检索层。** 裸奔的语义检索在Agentic SEO面前，一打就穿。Sybil攻击平均每个Top-5候选集塞进2.84个恶意克隆，攻击成功率93.2%。语义伪装61.14%。加三层检索验证，语义去重（相似度超85%的重复候选直接丢掉）、元数据行为一致性检测、权限申报合理性校验，攻击成功率大幅下降。Sybil从93.2%跌到26.59%，关键词堆砌从46.59%跌到7.83%，语义伪装从61.14%跌到9.82%。去重+行为校验+权限校验，基本把Planner面前的噪声扫干净了。

**Planner层。** 规划模型用Gemini 3.1 Pro。攻击方只改元数据，不改工作流——纯粹的"包装欺骗"。防线做元数据清洗：去掉描述里嵌入的Prompt注入模式、过滤虚假推荐标记、比对能力描述和权限申报的一致性。这步的关键在于：Planner看到的元数据必须被清洗干净，但清洗不能破坏合法技能的语义信息，否则会影响正常功能的匹配精度。

**执行层。** 运行时防线叫LifecycleGuard：每次工具调用前做动态污点追踪加策略校验。检测越权调用、非授权数据传输、跨步工作流中的信息泄露。不止监控单步，而是追踪敏感数据在整个多步工作流中的流向。

**进化层。** 技能每次更新被当成重新入库处理：重新验证来源、完整性、版本沿袭、依赖变更、语义一致性、权限修改。避免"今天信任的东西明天变成毒药"。论文专门强调了Publisher Compromise场景——攻击者拿到了合法开发者的密钥，推送一个"微小修复"但夹带了网络出站权限。没有重验证机制，这个更新就会安静地生效，Agent继续信任它，因为签名看起来没问题。

# 三层启示

**对Skill创作者的启示。** 写完Skill不是交差。权限申报必须和能力描述一致，膨胀的权限是攻防都盯着的战场。语义描述和可执行行为的对齐，不该靠一次性手工检查，应该自动化，论文里那条LLM语义验证线就是例子。每次更新Skill，版本变更至少过一遍一致性审验。

**对Agent平台建设者的启示。** 防线不该只糊在一层。检索器前面要仓库准入验证，Planner前面要元数据清洗，执行时要运行时监控，每次更新当成重新入库。SkillSec-Eval的架构把这思路模块化了：每道防线独立运作，攻击定位准，防线效果可单独量化。不用等全链路加固完，先从最弱的那道门开始。

**对Skill生命周期治理的启示。** 这篇论文和Agent-insight在做的事，同一条线。Agent-insight把Skill当成可治理的一等资产：评测、门禁、版本管理、运行观测、持续进化。SkillSec-Eval补安全维度：每个生命周期阶段定义具体的信任假设、攻击面和验证机制。安全不是附加功能，是Skill从创建到退役全过程中内嵌的治理维度。Agent-insight四维评测门禁里的"安全合规"，这篇论文的分类法能把它具体化，不再笼统地说"有不安全因素"，而是在仓库准入、检索、规划、执行、进化每层设对应的安全检查箱。
