# 让Agent写一篇维基百科长文，不是靠堆Prompt，是靠把写作拆成六步并用评测结果倒逼进化

---

# L3生成：三个"长"字叠在一起的难题

大模型写短东西已经很好了。摘要、回复、代码片段、对话——这些不用多说。

但真实世界的写作任务不是短回答。维基百科文章、技术报告、项目提案、分析文档——这类任务同时面对**三个"长"**：长上下文（查阅和整合大量资料）、长指令（同时满足结构、事实、风格、交付等多重约束）、长输出（几千甚至上万字的长文）。学界管这类任务叫L3生成。

三个"长"叠在一起，单次自回归生成就不够用了。长上下文会引发注意力失衡和信息丢失：经典的"迷失在中间"现象。长文章要求同时优化覆盖度、结构、连贯性、事实可靠性、风格和可交付性，单次生成没有任何中途质量检查。长输出让幻觉、重复、无依据的事实声明更容易出现：尤其当早期段落出了错，后续章节会把错误放大，或者错误被淹没在已组装好的文档里再也找不到。

思路很自然：分步写，或者多个Agent协作写。STORM是最接近这个方案的系统：它模拟维基百科作者和专家从多个视角探索话题，再生成大纲起草文章。问题在于，STORM里角色和能力被绑死在了Prompt模板和固定管道里。检索、过滤、写作紧耦合。没有独立的质量门。评测结果也不自然回流成可复用的写作规则。

清华SPMI实验室的GEIS（Generation–Evaluation–Improvement loop of Skills）走了另一条路。不是做一个更强的多Agent管道，而是**把长文生成的每个能力拆成一个独立的、可被评测驱动的、可进化的技能**。

# 六个阶段，一个可检查的写作过程

GEIS的核心不是模型，是**article-writer技能**：一份声明式的SKILL.md文件，把写作拆成六个显式的语义阶段。

**Request：重述边界。** 系统先重述目标、受众、输出类型和约束。缺失信息不靠猜，而是显式假设。"写给谁看"、"要什么深度"、"要不要图表"：这些不在暗处潜规则，在明处。

**Plan：建结构性合约。** 生成Section级别的提纲，不只是标题，还有预期深度、子话题、以及可视锚点（Visual Anchor）。可视锚是一个确定性占位符，给后面的图表渲染预留插入点。这一步是结构性合约：后续的草稿不能随意偏离。

**Draft：写完整文章。** 不是大纲加几句话，是正文。主要Section需要实质性段落、例子、领域术语。内容密度的最低要求被写死在阶段定义里。

**Audit：中途质量检查。** 系统自查结构、事实一致性、清晰度、可操作性、受众匹配度。这一步直接堵住了一个致命漏洞：单次管道把有缺陷的中间产物直接传给下游。

**Refine：定点修。** 薄弱的章节加深度、冗余的段落砍掉、缺失的证据或例子补上。Audit发现什么就修什么。

**Deliver：只输出结果。** 最终的成品发出去，中间笔记、规划痕迹全留在内部。避免读者看到"让我为您写一篇关于……的文章"这种AI痕迹。

六个阶段不是拍脑袋起的名字。论文把它类比为结构化编程：**每个阶段有明确的输入、输出和验证标准，出错时可以定位到具体哪个阶段出了问题。** 不是一团黑箱里"写得不好"的笼统结论。

# 写+查+画：技能之间的边界是明线

单一的写作流水线不够。长文章通常需要引用、实拍图和架构图。GEIS把这三件事拆成了独立技能。

**浏览器搜索和图像采集**委派给tasi-browser-automation技能。基于Chrome DevTools Protocol控制真实浏览器：打开页面、等待加载、提取语义快照、跟页面元素交互、提取内容。写作技能不负责底层网页导航，只提需求。

**架构图渲染**委派给architecture-diagram技能。输入结构化的组件关系描述，输出HTML/SVG图和PNG导出。

链接写作和视觉元素的机制是确定性的锚点标记。`[[DIAGRAM:id|title=...]]`是图表占位，`[[IMAGE:id|query=...|title=...]]`是真实图片占位。文本生成和下游渲染被彻底解耦：Markdown、Word、PDF管道可以独立解析这些锚点。锚点ID要求唯一，避免重复插图。

这种设计跟STORM的根本区别不是LLM调用次数多少，而是**抽象单位不同**。STORM把能力藏在角色Prompt和管道模块里，GEIS把每个能力声明为一个独立技能，用途范围可被单独检查、单独替换、单独优化。上下文加载也走渐进式暴露：只加载任务相关的技能，不把整个能力栈全部塞进去。对L3生成来说这很关键，上下文预算本来就紧张，无关指令混进去会干扰写作质量。

# 评测不是打一个分，是生成一份可执行的诊断

GEIS的评测不走"给一个总分然后不知道怎么办"的路子。它用的评测技能叫pdf-comparison-evaluation。

四维评分：结构质量（35分）：层级、连贯性、格式一致性、必要组件完整度；内容质量（35分）：任务对齐、正确性、深度；视觉质量（15分）：图片相关性、可读性、数据一致性、标题匹配；PDF交付质量（15分）：可搜索文本、字体稳定性、导航元数据、页面几何。

关键设计是**成对比较而非绝对打分**。同一话题的两篇文档放在一起对比，同一个评分卷轴同时量两篇。绝对分数跨调用容易漂移，很多质量差异本身也是比较性的：两篇关于同一话题的文章都可能内部自洽，但在深度、结构或覆盖面上差别明显。成对比较强制对称：哪一篇都不是"金标准"，路径顺序不影响评分严格性。

评测报告不是只有一个分数。它包含话题对齐、评分卡、算术验证、发现项清单和修订路线图。最后两项是关键：发现项告诉你是谁的问题（写作问题还是导出工具问题），修订路线图告诉你优先级和建议修复方向。评测输出是一份可执行的诊断，不是一页数字。

# 从评测到进化：把报告变成补丁

评测做完，闭环的最后一步是article-writer-improving技能。

它读评测报告，筛出写作技能管辖范围内的问题，映射到具体的写作规则目标，生成改进计划。一个关键的分诊逻辑：薄弱的章节、缺失的引用、糟糕的过渡、遗漏的结论：这些是写作问题，该改。缺失的书签或字体嵌入问题：这些属于导出工具，不该写进写作规则。

改进技能输出三级。计划级：解释根因和建议修复。会话覆盖级：下一次运行的临时约束。永久补丁级：当问题跨多份报告反复出现，直接修改技能本身。

在20个话题的改进实验中，反复出现的发现被合成为**八条永久补丁**：最低来源要求、事实陈述必须带内联引用、稳定图片来源、章节深度最低预算、段落间过渡桥、正式参考文献格式、话题完整性检查、强制结论段落。这些补丁不改模型权重。它们改的是模型遵循的写作流程。

# 两轮实验，三个关键数字

20个维基百科特色文章话题，覆盖历史、文化、软件工程、计算机科学、AI、网络、设计、传记。生成侧用GPT-5.4，评测侧用Qwen 3.5 Plus：生成器和裁判分离，降低自评偏差。

**第一轮：GEIS vs. 系统默认vs. STORM。** 100分PDF评分卷轴。GEIS比Tasi Harness默认写作高出8.0分（82.1 vs 74.1）。结构+2.6，内容+3.2，视觉+2.2，PDF交付持平：增益来自写作流程和视觉锚点机制，不是更好的PDF导出器。跟STORM比，两个可直接比较的写作维度上，GEIS的结构高出5.6分、内容高出2.2分。差距最大的还是结构：显式的Plan/Deliver合约和Audit/Refine质量门在维持章节边界和完整组件上起了作用。

**第二轮：改进实验。** 20个话题先写一遍，评测，用八条补丁修article-writer技能，再写一遍。平均分从82.90涨到**86.95**，涨了4.05分。增益几乎全来自内容维度（+3.85），结构几乎没变（+0.20）。这跟补丁的实际内容一致：补丁主要加强来源收集、内联引用、技术深度覆盖、正式参考文献和话题完整性，不改变Plan和Draft的基本流程。17个话题提升，3个话题微幅下降。下降案例揭示了统一补丁的天然限制：一个全局规则没法适应所有话题的敏感需求。某些话题在强引用要求下反而丢失了学术深度，有些失去了三级标题的实践结构。技能进化需要话题感知的策略，不能全搞一刀切。

# 换一个视角：长文写作从管道变成资产

GEIS这篇论文的本质命题不是"怎么写出更好的维基百科文章"。它是**把长文生成从固定多Agent管道，重构为一组可检查、可评测、可进化的技能资产**。

写作是一个六阶段的命名技能，而不是一个带Prompt的角色。检索、图像、图表各自是独立技能，通过渐进式暴露加载，不污染上下文。评测不是打一个分数就走，而是生成一份可执行的结构化诊断报告。改进不是凭感觉重写一篇，而是把反复出现的评测发现映射为技能文件里的永久规则变更。

这跟Agent-insight的Skill生命周期治理是同一个方向。Agent-insight用四维评测门禁决定Skill能不能上线、能不能推全。GEIS补的是"评测结果怎么闭环成Skill进化"的具体机制。评测发现 → 归因分诊 → 规则级修改 → 技能重跑验证。这一条线能让Skill从静态文本变成持续改进的活资产。

GEIS目前做的是离线闭环：20个话题写一轮，评一轮，改一轮，再写一轮验证。如果把评测常态化、发现归因自动化、补丁生成和验证自动化，长文写作就从"一个系统"变成了"一套可以持续校准的写作规则"。这才是Skill作为一等版本化资产的本意。
