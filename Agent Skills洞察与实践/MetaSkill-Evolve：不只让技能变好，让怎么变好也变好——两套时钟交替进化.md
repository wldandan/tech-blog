# MetaSkill-Evolve：不只让技能变好，让"怎么变好"也变好

> 论文：MetaSkill-Evolve: Recursive Self-Improvement of LLM Agents via Two-Timescale Meta-Skill Evolution
> 作者：Zefeng Wang, Minxi Yan, Jinhe Bi, Sikuan Yan, Volker Tresp, Yunpu Ma（LMU Munich、CUHK、MCML、MemAgentsLab）
> 发布时间：2026 年 7 月

---

## 一、技能会进化了，但进化的方式是写死的

技能（skill）是一段 Markdown 规范，告诉 Agent 某个任务该怎么执行。社区里出现了不少"技能自改进"系统——Agent 执行失败后，分析原因，重写技能文件，跑验证，迭代进化。EvoSkill、GEPA、SkillWeaver 这些工作在多个 benchmark 上已经拿到了显著提升。

但这里有个盲区。**技能本身在被持续改写，但进化的方式是固定的。** 分析器怎么诊断失败、检索器怎么找跨分支经验、分配器怎么定子代预算、提议器怎么生成编辑、执行器怎么落地——这五个环节的策略在整个进化过程中从不改变。

这意味着一个分支不能改进"自己怎么改进"。面对不同类型的失败——读错了表格，还是计算逻辑有误——它只能套同一套诊断流程。如果这套流程对这类失败不奏效，没有机制能修正它。

MetaSkill-Evolve 做的事：把改进过程本身变成一个可演化的对象。不只是技能在变，连"怎么进化"也在变。

---

## 二、核心思路：两套时钟，一套流水线

每个进化分支维护两个状态：**任务技能 s**（告诉 Agent 怎么做任务），**元技能 m**（告诉改进系统怎么改 s）。两者用同一种 Markdown 格式，区别只在作用对象。

元技能 m 由五个组件构成，各自控制改进流水线的一个环节：

- **ψ（Analyzer）**：怎么诊断失败？打什么标签、产什么分析？
- **σ（Retriever）**：怎么跨分支分享经验？按什么条件拉取修正案例？
- **α（Allocator）**：每个父节点该生成多少子代？什么时候该加大搜索？
- **π（Proposer）**：怎么根据诊断和检索结果提出编辑方案？
- **ε（Evolver）**：怎么把编辑写回技能文件并验证一致性？

这五个组件共同参数化了"从失败到改进"的完整链路。

进化在两个时钟上交替。**快时钟**每次迭代选一个前沿分支，用它的元技能 m 改进它的任务技能 s，产出子代。**慢时钟**每隔 H 次迭代触发一次，把过去 H 个迭代的整体表现——子代是否在持续变好——作为反馈信号，重新把同样的五 Agent 流水线作用到元技能 m 上，改进 m 本身。

**没有引入任何新模型或新框架。** 同样的五个 Agent、同样的 Markdown 格式、同样的"分析→检索→分配→提议→执行"流水线，唯一的区别是目标文件从 task-skill 换成了 meta-skill。所有五个 Agent 共享一个冻结的基座模型，不微调。

## 三、怎么选下一个进化的分支

每次迭代要决定从哪个分支继续进化。贪心选最高分容易陷入局部最优，随机选浪费算力。

MetaSkill-Evolve 用三因素前沿评分挑父节点：

**前沿评分 = η₁ · U(s) + η₂ · P̂(m|s) + η₃ · N**

- **U(s)**：技能在验证集上的准确率。标准指标——当前技能有多好。
- **P̂(m|s)**：元生产力。这个分支最近 H 个孩子的平均效用增益。衡量"这个分支的改进策略有没有在持续产出更好的后代"。一个技能分数中等但改进策略一直在往上走的分支，比一个分数高但改进停滞的分支更值得投入。
- **N**：选型冷却。分支被选越多，再次被选代价越高，防止少数分支垄断预算。

三个因素各扛一种失败模式。只靠 U 会被高分死胡同卡住，只靠 P 会把预算全投进一条血统，只靠 N 变成随机搜索。三元组合让搜索在利用和探索间自动平衡。

## 四、两套时钟的细节

### 快时钟：任务技能进化

从选中的父节点出发，恢复到它记录的盘上快照（s 和 m），在训练集上跑一遍，找得分最差的样本作为诊断目标。这是故意的——挑最差案例不挑平均案例，因为最差的能暴露技能里最需要修的部分。

最差案例交给 Analyzer 分析，打标签 ϕ、出分析 a。Retriever 按 ϕ 从进化图 G 拉取标签匹配的跨分支修正案例。Allocator 根据当前分支的进化历史决定这轮产多少个孩子 K。Proposer 对每个孩子生成不同的编辑提案 δ。Evolver 把 δ 翻译成文件写入，做前后哈希校验确认文件确实被改了。每个孩子在验证集上评估，算出 ΔU。

所有孩子——不管 ΔU 正负——都记录在进化图 G 里。只有 **ΔU > 0** 的孩子进入档案，有资格被选为将来的父节点。ΔU ≤ 0 的孩子不能做父节点，但保留在图里作为检索器的可引用经验。

### 慢时钟：元技能进化

每 H 次迭代触发。把过去 H 个孩子的标签、诊断、结果和平均 P̂ 装进一个**合成元故障 trace**——把一段进化历史伪装成训练样本的样子，这样同一套 Analyzer prompt 就能同时用于任务技能和元技能的诊断。

然后重跑五 Agent 流水线，目标从 task-skill 文件换成 meta-skill 文件。

慢时钟有三个和快时钟不同的操作细节。Analyzer 被约束为只诊断 m 里最有责任的一个组件，诊断不出按轮转 fallback。**整体重写**指每条子代同时编辑全部五个 meta-skill 文件，Proposer 串行出方案、Evolver 并行落地，保留跨组件一致。**增量累积子代**指第 k+1 个子代读的是第 k 个子代已经写过的文件，不是父节点原始文件——一步步增量精炼，而非 K 个独立编辑各自撞上去。

## 五、实验结果

在 OfficeQA、SealQA、ALFWorld 三个 benchmark，所有 Agent 共享冻结的 Gemma-4 31B。对比四种设置：No-Skill、Static Skill、Single-Level Evolution（任务技能进化但元技能固定）、MetaSkill-Evolve（两套时钟都跑）。

| Benchmark | vs No-Skill | vs Single-Level |
|-----------|------------|----------------|
| OfficeQA | **+23.54** | **+6.38** |
| SealQA | **+16.09** | **+8.05** |
| ALFWorld | **+1.92** | **+1.92** |

OfficeQA 和 SealQA 上，No-Skill → Static → Single-Level → MetaSkill-Evolve 是单调上升线。ALFWorld 上基座已接近饱和，改进空间小，但没有退化。

**所有增益来自技能和元技能的演化。** 基座冻结，没微调，没加新模型，没加训练数据。

---

## 六、总结

MetaSkill-Evolve 把 Agent 自改进的递归层级往前推了一步。

此前的系统让"做什么"可以变，但"怎么变"是写死的。MetaSkill-Evolve 让"怎么变"也成了可演化的技能，用同一套流水线、同一种格式、同一个模型。Agent 不只是从经验里学到更好的任务策略，还能学到更好的学习策略——什么样的失败值得深入分析、什么时候该从其他分支借经验、什么时候该加大搜索力度。这些决定不再是全局固定的，每个分支可以有自己的方式，且这种方式本身会被选择压力优化。

元生产力 P̂ 把分支"持续产生改进后代的能力"从当前技能分数里分离出来，让搜索可以投资在"正在变好的方向"而非"现在看起来最好的状态"。这对任何需要管理多个并行进化血统的系统来说，都是一个值得参考的设计。
