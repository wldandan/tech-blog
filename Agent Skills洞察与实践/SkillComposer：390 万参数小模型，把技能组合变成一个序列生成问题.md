# SkillComposer：把技能组合变成一个序列生成问题

> 论文：Generative Skill Composition for LLM Agents
> 作者：Xinyu Zhao, Zhen Tan, Vaishnav Tadiparthi, Nakul Agarwal, Kwonjoon Lee, Ehsan Moradi Pari, Hossein Nourkhiz Mahjoub, Tianlong Chen（UNC Chapel Hill、Arizona State University、Honda Research Institute USA）
> 发布时间：2026 年 7 月
> 项目页面：https://skill-composer.github.io/

---

## 技能库变大了，选技能反倒成了瓶颈

LLM Agent 社区这几年在技能（skill）这件事上投入了很多。技能封装了模块化的过程性知识——比如"搭建沙箱环境""跑回归测试套件""跨多个文件重构一个函数"。一个 Agent 在推理时动态加载相关技能到上下文中，就能显著提升它处理复杂任务的能力。

越来越多的团队在构建和维护技能库，技能的数量在涨。这就把推理时的瓶颈从"技能够不够"变成了**"该选哪些技能、选几个、按什么顺序执行"**。

现有的做法大致分两路。一路是**直接推理**：把所有技能描述都塞进 Agent 的 prompt，让它自己看着办。另一路是**检索**：用 embedding 相似度或 LLM 打分对技能排序，取 top-k。两种思路都有道理，但它们都忽略了一个关键问题：**技能组合是一个结构性的联合决策——选哪些、选几个、按什么顺序，这三个维度不能拆开。**

检索给你一个无序的候选列表，没法告诉你需要几个技能。直接推理把组合决策隐式地嵌入在非结构化的推理轨迹里，你拿不到一个可检查的显式计划。

举个例子：用户要求"定位一个已废弃的 API 调用，在整个代码库中重构它，然后跑回归测试"。正确的做法是先搜（找到所有调用点），再改（批量重构），最后测（验证变更）。检索能分别找到搜索、编辑、测试相关的技能，但一个排序列表不会告诉你该用几个技能、顺序怎么排。直接推理也许能兜出来，但每次都要把整个技能库（可能上百个）塞进 prompt，成本高不说，还容易漏。

UNC Chapel Hill、Arizona State University 和 Honda Research Institute USA 的团队把这个问题形式化为**任务条件的技能序列预测**，提出了 **SkillComposer**：一个只有约 390 万可训练参数的小模型，把技能子集选择、数量预测和顺序编排统一在一次自回归解码里。

## 形式化：把技能组合变成序列预测

论文的形式化很干净。给定一个任务描述 x、环境上下文 c、一个固定的技能库 S = {s₁, ..., s_K}（K = 196），模型预测一个变长的技能索引序列：

**z = (z₁, z₂, ..., zₙ, STOP)**

每个 zₜ 对应技能库中的一个索引，STOP 表示序列结束。预测出的技能数量 n 由 STOP 出现的位置决定。索引查表后得到最终的有序技能计划。

这个序列预测同时解决了三件事：**子集选择**（哪些技能相关）、**数量预测**（需要几个技能）、**顺序编排**（按什么顺序组合和执行）。这三个东西以前是分开处理的，或者根本没有被显式处理。

图 2 给了个很好的例子：任务是在洪水数据分析中"找到密歇根州 2025 年 4 月第一周出现洪水的 USGS 监测站，输出 station_id 和 flood_days"。模型拿到任务描述、环境文件（监测站数据）、196 个技能的压缩元数据，输出索引序列 (104, 184, 55, STOP)，解析后对应 (nws-flood-thresholds → usgs-data-download → flood-detection)。先拿阈值标准，再下载数据，最后做洪水检测——顺序是对的。

## 模型设计：小解码器 + 两个辅助头 + 检索先验

SkillComposer 由三部分组成，结构并不复杂。

### 1. 冻结编码器 + 轻量自回归解码器

编码器用 Qwen3-Embedding-0.6B（冻结，不训练），把序列化的 prompt（任务 + 环境 + 196 个技能的压缩元数据）映射成一个 256 维的任务向量。

解码器是一个 3 层、256 维、4 个注意力头的 mini Transformer，输出词汇表就是 {1, ..., 196} ∪ {STOP}。每一步的预测以任务向量和已生成的前缀为条件，技能之间的转移依赖被自然地捕捉在自回归过程中。技能元数据的 embedding 通过交叉注意力输入解码器，所以解码器能通过自然语言描述区分每个技能，而不是只靠编号。

**总共只有约 390 万可训练参数。** 对比 SFT 基线（全量微调 Qwen3-0.6B 的 6 亿参数），小了约 154 倍。

### 2. 两个辅助头：把被 AR 稀释的信号捡回来

自回归头管顺序——每次预测都以前缀为条件，这很合理。但"需要几个技能"和"哪些技能相关"这两个信号在 AR 目标里被稀释了：数量的信息只靠一个 STOP token 来传递，每个相关技能的正向监督只在它出现在正确位置的那一步才生效。

所以 SkillComposer 额外加了两个任务条件的辅助头，都挂靠在任务向量 h_x 上：

- **数量头（Cardinality Head）**：一个线性分类器直接预测需要几个技能（1~8），提供独立于 STOP 的长度信号。
- **集合头（Set Head）**：一个双 MLP 匹配器对每个技能独立打分，判断它是否属于当前任务的技能集合。每个相关技能都能收到独立于位置的梯度信号。

训练时这三个头联合优化。推理时，数量头可以软偏置或硬截断解码长度，集合头的分数作为 logit 融合的一项先验。

### 3. 检索增强解码：TF-IDF 比稠密向量更好用

解码时每一步的 logit 由三项融合：**上下文 logit（来自 AR 解码器）+ 检索先验（TF-IDF 余弦相似度）+ 集合成员先验（来自 Set Head）**。STOP token 不接收检索和集合偏置，终止由 AR 独自决定。

有个反直觉的发现：**稀疏检索（TF-IDF）在解码时比稠密向量（Qwen3-Embedding）好，高出 +2.5pp Set F1。** 原因是这个封闭技能库只有 196 个技能，技能名称简短且语法特征明显，token 级重叠在区分它们时精度很高；稠密向量在更宽的语义上下文中做平滑，反而容易过泛化。

但任务编码器那块，稠密向量是更好的选择。SkillComposer 的做法是**编码用稠密（Qwen3-Embedding），解码偏置用稀疏（TF-IDF）**，各取所长。

## 数据构建：基于真实技能库 + 技能依赖图

训练数据怎么来是一个容易被忽略但实际很关键的问题。SkillComposer 的起点是 SkillBench 的 65 个人工标注的软件工程任务，每道题自带 gold skill 标注。团队从这些种子出发，做了两件事：

首先，基于技能元数据和实际工作流共现，构建了一个 **196 节点、924 条边的技能依赖图**。边分两种：依赖边（上游的输出类型和下游的输入类型重叠，编码硬数据流顺序，658 条）和工作流边（在真实任务轨迹中共同出现，编码经验顺序，266 条）。

然后，用 Gemini 2.5 Flash/Pro 做分层合成：单技能任务（2880 条，覆盖全部 196 个技能，校准"只用一个技能就停"的行为）和多技能任务（6927 条，覆盖 2~5 个技能的组合，合成时显式注入依赖边的排序约束）。合成后经过三层去重验证（精确匹配 → 字符 trigram Jaccard → 句子 embedding 余弦）。

最终得到 9872 条训练记录，90/5/5 分割。

## 实验结果：小模型 + 结构化 = 更好的组合

### 技能预测质量

在分布内测试集（n=494）上，SkillComposer 以 73.9% Set F1 领先 SFT 的 71.1%（+2.8pp），比 LLM-judge（Gemini-2.5-flash 直接对 196 个技能打分排序）高出 +12.9pp。这个差距在单技能任务（k=1）上最大——原因很简单，多选了一个不该选的技能就会被狠狠惩罚，SkillComposer 的数量头在这里起作用。

**真正有说服力的是分布外测试。** 从训练集中完全移除 65 个真实任务，只用合成数据训练，然后在 65 个真实任务上测试。SFT 的 Set F1 从 71.1% 暴跌到 43.6%，损失了 27.5pp。SkillComposer 从 73.9% 降到 62.9%，只损失 11pp。一个 +19.3pp 的差距，用的是完全相同的训练数据和技能库。

SFT 崩的原因很好理解：它记住了合成数据的模板分布，当真实任务的措辞风格不一样时，没有鲁棒的先验可以依赖。SkillComposer 的冻结检索编码器 + 稀疏解码先验的组合，正好提供了这种分布外泛化的偏置。

### 下游任务表现：SkillsBench × 两个生产级 Agent

在 SkillsBench 的 75 个任务上，用 GPT-5.2-Codex 和 Gemini-3-Pro-Preview 两个生产级 coding agent 实测：

| 技能条件 | GPT-5.2-Codex Pass↑ | Gemini-3-Pro Pass↑ | Codex Token↓ |
|----------|---------------------|---------------------|-------------|
| No Skills | 22.2% | 25.8% | 0.94M |
| All Skills（196个全塞） | 29.3% | 38.7% | 1.27M |
| Retrieval (top-3) | 44.0% | 41.8% | 1.09M |
| Retrieval (oracle) | 44.0% | 42.2% | 1.13M |
| **SkillComposer** | **45.3%** | **44.0%** | **1.03M** |
| Gold Skills（上界） | 51.1% | 48.4% | 1.12M |

几个看点：

- No Skills 到 Gold Skills 之间有大约 +25pp 的提升空间。把全部 196 个技能糊进 prompt（All Skills）只吃到了一小部分，token 成本反而飙到 1.27M。**技能不是越多越好，上下文灌满不等于组合正确。**

- SkillComposer 以 45.3%/44.0% 的通过率超过两个 agent 上的所有非 oracle 基线，追平甚至略超 Retrieval (oracle)，而且用的是最小 prompt 预算（1.03M token）。这大约填上了 Gold Skills 上界 80% 的空间。

- Retrieval (oracle) 已经是知悉 gold 技能集合的上限检索了，SkillComposer 没有用到任何 oracle 信息，却能在更低的 token 成本下打平或超越它。

### 消融：每个组件都在扛活

AR 头单独跑只有 69.3% Set F1。加上 Set Head（仅在训练时）→ 71.8%（+2.5pp）。推理时关掉 set-fusion 偏置 → 掉 7.1pp。关掉 TF-IDF 检索先验 → 掉 4.6pp。**三个信号通道都不可或缺。**

解码偏置换用稠密向量（Qwen3-Embedding cosine）代替 TF-IDF → 降低 2.5pp。换 BM25 → 降低 3.9pp。在这个场景下，稀疏的 token 级重叠比稠密语义匹配更有区分度，技能名和描述之间的 n-gram 特征足够用了。

## 这意味着什么

SkillComposer 的核心洞察有三个层次。

**第一，技能组合是一个结构性预测问题，不是检索问题。** 拿一个排序列表，你不知道该停在第几个。把所有技能塞给 Agent 让它自己想，你拿到的是隐式推理。显式地预测有序的、有终止符的技能序列，既省 token，又可检查，还能直接加载进下游 Agent 的执行上下文。

**第二，小专家可以打赢大通才。** 390 万参数 vs 6 亿参数，训练计算量少了约 25 倍，SkillComposer 却在分布外真实任务上甩开 SFT 近 20 个点。对于一个封闭的技能库，**懂得利用库结构的专用模型，比放大通用 LM 更可靠。**

**第三，稀疏先验在封闭词汇表场景下被严重低估了。** TF-IDF 这种老派方法在 196 个短技能名的区分上超过了稠密向量，差了 2.5pp。不是所有问题都需要 embedding。

对正在构建或维护 Agent 技能库的团队来说，SkillComposer 给了一个方向：别把技能选择外包给检索系统或靠 Agent 自己悟，用一个小的、任务条件的序列预测器来显式建模组合过程。效果更好，成本更低，而且在技能描述措辞风格变化时，泛化能力更稳。
