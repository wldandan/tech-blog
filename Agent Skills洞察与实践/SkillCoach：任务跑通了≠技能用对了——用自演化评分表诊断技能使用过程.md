# SkillCoach：任务通过了不代表技能用对了——用自演化评分表诊断 Agent 的技能使用

> 论文：SkillCoach: Self-Evolving Rubrics for Evaluating and Enhancing Agentic Skill-Use
> 作者：Jiayin Zhu, Kelong Mao, Yudong Guo, Dengbo He, Sulong Xu, Simiu Gu, Yutao Yue（HKUST(GZ)、京东）
> 发布时间：2026 年 7 月

---

## 一、问题：任务能跑通，不等于技能用对了

LLM Agent 的技能库正在成为企业部署的基础设施。技能把 SOP、领域规则、工具链、脚本和验证流程打包成可复用的操作单元。Agent 接到任务后，从库中选技能、按流程执行、组合多个技能、检查输出——这四件事做对了，任务才算真正用好了技能。

但这里有个容易被忽略的问题：**最终验证通过（verifier pass）不等于技能使用正确。** 一条轨迹可能通过了外部验证，但它选了干扰技能、跳过了关键步骤、靠试错蒙对了答案，或者提交前忘了检查。只看最终结果，这些全被掩盖了。

论文给了一个例子。同一个任务，轨迹 A 先读了正确的技能文档，按流程下载了洪水阈值数据，再跑检测脚本，最后检查输出才提交。轨迹 B 同样通过了验证器，但它没看技能文档，自己瞎试，碰巧也输出了正确结果。**按照"跑通了就是好"的逻辑，两条轨迹都会被当成正例用于训练。** 但显然 A 才是可复用的技能使用行为，B 是运气。

这就引出了 SkillCoach 要做的事：**用一套自演化的评分表（rubric），从过程维度评估 Agent 的技能使用，把"任务做对了"和"技能用对了"分开。**

---

## 二、四个维度：技能使用到底该怎么评

SkillCoach 把技能使用拆成四个过程维度，每个维度都独立于最终验证结果：

**① 技能选择（Skill Selection）**：Agent 是否选对了 gold 技能，同时避开了干扰技能？用集合级 F1 来算——漏选了 gold 技能扣分，选了干扰技能也扣分。如果根本没有适用技能，Agent 应该主动选择不使用技能，而不是硬选一个相似的。

**② 技能遵循（Skill Following）**：Agent 是否按技能文档里规定的关键步骤执行了？每个关键步骤有完成度评分（0/0.5/1），而且必须有轨迹中的可观测证据支撑——不能只声称"我做完了"。缺少证据、跳过脚本执行、声称完成但轨迹里看不到，都扣分。

**③ 技能组合（Skill Composition）**：当任务需要多个技能或子流程协作时，执行顺序对不对？中间产物有没有正确传递？比如上游技能输出的数据，下游技能有没有正确接入。单技能任务这个维度不适用。

**④ 技能反思（Skill-Grounded Reflection）**：提交前 Agent 有没有做显式检查？验证输出文件、格式、schema、任务特定约束。反思不是验证器——验证器是外部跑完所有步骤后的最终判定，反思是 Agent 自己在提交前主动执行的检查行为。

**外部验证器被刻意独立在外。** 这是整个框架的关键设计选择。验证器告诉你"结果对不对"，四个维度告诉你"过程对不对"。两者分开，你才能区分可靠技能使用和偶然任务成功。

## 三、评分表怎么自演化

为每个任务手写评分表很费事。SkillCoach 的做法是：**从 gold 技能中自动生成初始评分表，然后在真实 rollout 上跑评估，根据暴露出的问题自动打补丁，再用验证集把关。** 整个过程是一个带质检的迭代循环。

### 初始构建

从 gold 技能文档、任务描述、验证器信息中提取关键步骤列表。每个步骤映射到可观测事件——读了什么文件、调了什么脚本、产出了什么中间产物、最终写了什么输出。初始评分表 R0 定义了每个维度的评分规则、证据要求和负面案例。

### 轨迹评估

让 Agent 在真实环境中跑一遍（带着 gold 技能和干扰技能混合的技能库），拿到完整轨迹。用 LLM 做 judge，从轨迹中提取可观测证据（技能读取、工具调用、文件编辑、脚本执行、验证尝试），然后按当前评分表逐维度打分。正面评判必须引用证据，不能只说"看起来不错"。

### 验证把关的演化

每轮演化把 rollout 分成校准集和验证集。单独用一个仲裁模型分析当前评分表在校准集上的表现，提出局部补丁。补丁可以加证据要求、补充负面案例、收紧评分条件、增加顺序依赖，但不允许删除关键步骤、绕过验证器，也不允许访问验证集。补丁候选先在验证集上跑，通过硬门禁（比如不能把选干扰技能的行为标记为正确）和软指标（证据覆盖度、证据质量、与验证器一致性、紧凑度）双重检验，才能被接受。

每轮选验证集上表现最好的版本，作为下一轮的基础。最终产出该任务的 R_best。

**这个演化确实有效。** 人工标注对比 R0 和 R_best：gold 关键点覆盖率从 71.56 提升到 83.70，可用性从 81.53 分提升到 94.33，幻觉率从 2.00 降到了 0.00，轨迹筛选一致性从 82.00 提升到 96.00。评分表本身在变好，不只是评估工具更准了，而是作为诊断工具更可信了。

## 四、实验：诊断、筛选、边界

### 过程维度暴露了最终准确率藏起来的失败

在 Gold+Distractors 设定（gold 技能 + 2 个无关干扰 + 3 个语义相似干扰）下测试了 7 个模型，结果很清楚：

- **加上 gold 技能确实大幅提升了任务成功率**（比如 Opus 4.7 从 18.0 跳到 88.0，GPT-5.5 从 24.0 跳到 80.0），说明任务确实是技能依赖型的。
- **但加上干扰技能后，几乎所有模型的最终准确率都降了**——即使 gold 技能还在库里。问题不是"有没有技能"，而是"能不能在干扰里找到对的"。
- 过程维度揭示了具体失败模式：Gemini 3.1 Pro 的最终准确率从 72 降到 70，看着还好，但**它的技能选择 F1 从 98.0 暴跌到了 78.0**。Qwen3.5-9B 更惨，选择 F1 从 92.0 掉到 44.0。这些崩在"选技能"这一步，不拆开根本看不到。

### 评分表筛选 SFT 数据比结果筛选好得多

用评分表筛选训练数据，看能不能提升 Agent 的技能使用能力。在 Qwen3.5-4B 和 9B 上做 SFT：

| 训练数据筛选方式 | 4B 最终准确率 | 9B 最终准确率 |
|---------------|------------|------------|
| 基准（不训练） | 8.0 | 14.0 |
| 结果筛选（只看 verifier pass） | 6.0 | 18.0 |
| R0 评分表筛选 | 16.0 | 28.0 |
| **R_best 评分表筛选** | **24.0** | **32.0** |

几个信号很明显。结果筛选基本没用——4B 还降了。R_best 比 R0 好，说明评分表演化确实有用。四个维度中，去掉关键步骤遵循损失最大（4B 掉到 10.0，9B 掉到 16.0），其次是去掉组合顺序，去掉反思影响相对小但可见。

### 技能库多大时选择会崩？

论文做了一个很有趣的 stress test：把技能库从只有 gold 技能一直扩到 50000 个干扰技能，看模型的选择能力在什么规模开始退化、什么规模崩溃。

定义了两个边界：
- **退化边界**：选择 F1 相比无干扰基线首次跌了 ≥0.10，且之后不再恢复。
- **崩溃边界**：80% 的样本完全选不到 gold 技能。

小模型最早退化：DeepSeek V4 Flash 在约 26-27 个干扰时就开始了。强一点的晚一些：GPT-5.5 约 55-56 个，Opus 4.7 约 194-195 个。崩溃的差距更大：DeepSeek V4 Flash 在约 6400 个干扰时就崩了，GPT-5.5 和 Opus 4.7 即使在 50000 个干扰下也没有触发崩溃标准。

干扰类型的影响也很明显。同量级（50 个）下，随机无关技能对选择 F1 的影响最小，同领域技能影响中等，**高语义相似度的干扰最致命**。拿 GPT-5.5 来说，无关干扰下选择 F1 是 0.84，高相似度干扰下掉到了 0.59。最危险的从来不是明显不搭的技能，而是看起来很像的那种。

## 五、总结

SkillCoach 这件事，最核心的贡献是把它技能使用的评估从"看结果"推到了"看过程"，而且把过程评估本身做成了一套可自演化、可验证的体系。

"结果通过即可"这个逻辑对技能使用是不成立的。选了错技能但碰巧修正、跳过关键步骤但碰巧蒙对、提交前不做检查但碰巧输出格式对——这些轨迹从结果上看都是"成功"，但它们根本不是可复用的技能使用模式。把过程评分表和外部验证器分离开，是整篇论文最扎实的设计决策。

评分表演化不依赖预标注数据，靠真实 rollout 暴露的缺陷驱动的仲裁补丁，加上验证把关，这个闭环运行起来比想象中稳定。幻觉率降到零这件事尤其说明问题——补丁和质检的组合防止了评分表变"完善"但变"假"。

对做 Agent 技能库或 Agent 评估的人来说，分维度看技能使用、把过程评分表做成可演化的独立模块，这两条思路值得放进工程实践里。
