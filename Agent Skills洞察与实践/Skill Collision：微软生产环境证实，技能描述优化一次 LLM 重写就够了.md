# 一次重写就够了：来自微软生产环境的技能描述优化实战经验

> 论文：A Single Rewrite Suffices: Empirical Lessons from Production Skill Description Optimization
> 作者：Yangqiaoyu Zhou, Mohammad Alqudah, Kwei-Herng Lai, Aaron Halfaker, Yingqi Xiong, Yaar Harari（Microsoft）
> 发布时间：2026年6月
> 关键词：Skill Collision、LLM Agent、Routing、Description Optimization、Production ML

---

## 引言：当两段描述长太像时，AI 路由器就懵了

现代企业级 AI Agent 的典型架构是这样的：用户发来一条消息，LLM 规划器（planner）根据消息内容将其路由到某个专业技能——查日历的归日历，搜人的归搜人。**路由的依据，就是每个技能的自然语言描述。**

听起来挺合理的。但当技能数量膨胀到几十个、描述之间开始互相"撞脸"时，问题就来了。

想象一下：你的企业助手有一个 PeopleSearch 技能（"查找组织中的人员档案信息"），还有一个 GetUserManager 技能（"检索组织中的人员信息"）。用户问"Sarah 的经理是谁？"——路由器看了看这两个描述，选了 PeopleSearch。错了，该选 GetUserManager。这就是论文所谓的 **Skill Collision（技能碰撞）**：语义重叠的技能在同一个查询群体中互相争抢，路由器的决策被糊住了。

传统上，解决这个问题靠的是人——开发者写一版描述，部署上去，盯着真实流量或合成流量找路由错误，再手动改描述，再部署，再看…… 每上一个新技能，这个循环就得走一遍。一个技能平均要花掉 **120 分钟**的工程时间。当 Agent 技能数量持续增长，这显然不是什么可扩展的玩法。

微软的研究团队把这件事自动化了，然后在自己的生产环境企业群聊 Agent（9 个技能，372 个回归测试用例）和 ToolBench（约 16000 个工具）上做了一整套系统性消融。结论出人意料地简洁：**一次 LLM 重写就够了。**

---

## 核心问题：技能碰撞从哪来？

Skill collision 最痛的时候不是日常运行，而是**技能上线（onboarding）阶段**。新技能加入已部署的 Agent 时，它的描述必须精准地定位到所有现有技能的"夹缝"里——不能跟任何已有技能撞车。在只有三五个技能的时候，这还好办。九个、二十个、五十个技能的时候，人脑已经处理不了这种组合复杂度了。

论文把问题拆成两类：

**第一类：描述不精确导致的假性碰撞。** 两个技能干的活本来不同，但描述写得太像，路由器分不清。这类可以通过优化描述文本来解决。

**第二类：技能范围本身重叠导致的真性碰撞。** 两个技能在功能上就是有交集的——比如一个"知识检索"和一个"人员搜索"，当用户问的是组织知识类问题时，两者都能沾上边。这类碰撞**改写描述没用**，需要的是架构层面的调整（比如重划技能边界、加意图路由规则）。

识别这两类碰撞，论文也给出了一个很实用的诊断信号，这个后面细说。

## 方法：把人的调试循环交给 LLM

自动化流水线分两步，简单到你可能觉得"就这？"。

**第一步：LLM 初始化。** 给定技能名称，让 LLM 直接生成一段候选路由描述。不需要太多 prompt engineering，就是描述一下这个技能干什么的。

**第二步：错误反馈精炼。** 把初始描述放到一组有标注的训练查询上跑一遍路由评估，收集三类信号：

- **FP（False Positive）**：不该路由到这个技能的查询，错误地被路由过来了。
- **FN（False Negative）**：应该路由到这个技能的查询，却漏掉了。
- **TP（True Positive）**：正确路由的查询（用来平衡 prompt 里的正负例）。

然后把当前描述、最多 5 个 FP 和 5 个 FN 案例、等量的 TP 案例一起喂给 LLM，让它分析路由失败的模式，重写描述。重复这个循环最多 N 次，或直到训练 F1 超过 90%。最终选取训练 F1 最高的那版描述。

**单次重写变体（Single-Shot）**：把所有可用的 FP/FN 案例一次性扔进 prompt，让 LLM 直接产出一版改写描述，不迭代。这是后面对比实验的关键角色。

## 实验结果：自动优化打平人工调优

### 生产环境：9 技能 Agent

在微软的 enterprise group chat agent 上，包含 9 个技能（人员搜索、网页搜索、日历、内部知识检索、组织层级查询、邮件、文档生成等），372 个合成回归测试用例。

| 描述来源 | 平均 F1 | 与人工差距 |
|----------|---------|-----------|
| 人工调优（当前部署版本） | 79.4% | — |
| LLM 初始化（无反馈） | 78.4% | -1.0% |
| **单次 LLM 重写（Single-Shot）** | **79.2%** | **-0.12%** |
| 迭代精炼（Iter） | 79.2% | -0.20% |

自动生成的描述和人工调优版本的差距只有 **-0.12%（单次）到 -0.20%（迭代）**，两者都远在多次运行的标准差 ±0.78% 之内。换句话说，**自动描述和人工描述在统计上没有显著差异。**

但效率差异是巨大的：人工调优一个技能平均耗时 **120 分钟**，自动化流水线只需要 **3.8 分钟**，提速 **32 倍**。

### ToolBench 大规模验证：~16000 个工具

为了验证结论的泛化性，团队在 ToolBench 上做了更大规模的实验。重点是 open-world（检索式路由）和 closed-world（固定候选池路由）两种设定。

在 open-world 下，基线 F1 约 70%，单次重写带来了 **+4.45% 的 F1 提升**，几乎追平了 max-10 迭代精炼的 +4.65%（差距仅 0.2%）。即使把迭代预算拉到 max-30，也才到 +5.07%。

在 closed-world 下，基线 F1 本来就高（约 91%），优化增益相应较小（0.6-0.9%）。

## 最狠的发现：那些复杂机制基本没用

论文原本设计的流水线包含了不少直觉驱动的高级机制：什么对比式反馈（同时展示 FP、FN、TP）、迭代精炼到固定预算、对最易混淆的对手技能同时编辑（dual editing）、精调训练集大小……

然后他们做了一个系统性的消融实验，把每个设计维度单独拆出来测。

结果可以用一句话概括：**所有这些设计选择对最终 F1 的影响都不超过 0.5%。**

具体来说：

- **反馈信号类型**：FP+FN+TP 全集、只要 FP、只要 FN、不要 TP…… 差距全在 0.1% 以内。
- **迭代 vs 单次**：单次重写（+4.45%）和 max-10 迭代（+4.65%）差距 0.2%。
- **同时编辑混淆对（dual editing）**：开或关，几乎没区别。
- **每轮采样 5 例 vs 全量案例**：一样。
- **训练集大小（5/10/20）**：差距不超过 0.5%。

**真正驱动优化效果的，是错误反馈信号本身**——只要有 FP 和 FN 案例让 LLM 看到"我哪里搞错了"，它就能写出更好的描述。至于这些案例以什么形式、分几轮、带不带额外的复杂包装，都不太重要。

如果你要在实践中做 trade-off，结论很直接：**单次 LLM 重写是性价比最高的选项。** 长迭代预算在 open-world ToolBench 上能抠出一点边际收益，但额外成本几乎不划算。

## 你可能踩的两个坑

### 坑一：closed-world 和 open-world 是两个世界

论文发现了一个方向性的反转：**LLM 初始化在检索式（open-world）路由中有帮助（+1.5-2.1% F1），但在固定候选池（closed-world）路由中反而有害（-0.8-1.4% F1）。** 针对 closed-world 优化出的描述，拿到 open-world 下效果很差。

原因不难理解：closed-world 的候选池固定且小（3-15 个工具），优化更侧重于在一个已知的小圈子里做精确区分。open-world 的检索池动态且庞大，描述的质量还影响"能不能被检索回来"（recall），而不仅仅是"从候选里选对"（precision）。两个 regime 需要分开优化，不能混用。

### 坑二：有些碰撞靠改写描述救不了

团队发现了一个很实用的诊断指标：**初始训练 F1（iter-0 training F1）**。在 ToolBench open-world 上，iter-0 训练 F1 低于 65% 的工具，后续优化的验证集增益平均达到 **+6.27%**；而 iter-0 高于等于 65% 的工具，平均增益只有 **+0.63%**，差了大约 10 倍。

但更有意思的是反例。在微软自己的生产系统里，有两个技能（IntKnowledge 和 WorkbackPlan）的 iter-0 训练 F1 很低，训练阶段的优化增益也很大，但一到测试集就歇菜了，始终追不上人工基线。论文的诊断是：**这两个技能跟其他技能在功能范围上本身就重叠**——IntKnowledge 检索人员相关的组织数据，天然碰 PeopleSearch；WorkbackPlan 生成结构化计划，表面形式上碰 StatusReport。**描述写得再好，也解决不了"两个技能的活本来就差不多"这个问题。**

所以实操建议是：遇到 iter-0 训练 F1 低且训练/验证 F1 差距大的技能，优先考虑架构层面的调整（技能范围重构、引入意图专用的路由规则），而不是继续在描述文字上死磕。

## 总结：一张极简的操作清单

这篇论文的气质跟很多"全垒打式"的方法论文不同——它不自洽地承认自己最初设计的很多机制是多余的，然后把结论压缩成一个实操性极强的清单：

1. **用单次 LLM 重写替代人工调优。** 给它所有的 FP 和 FN 案例，一次就够了。迭代不迭代差别不大。
2. **匹配优化 regime 到部署 regime。** closed-world 和 open-world 的路由优化不要混用，LLM 初始化在 closed-world 下反而可能帮倒忙。
3. **用 iter-0 训练 F1 做优先级排序。** 低于 65% 的技能才是描述优化的主战场，高于 65% 的优化空间有限。
4. **训练/验证 F1 差距大 = 别写了，改架构吧。** 如果训练上去了但验证上不去，那是技能边界的问题，不是措辞的问题。

对于正在搭建或维护企业级 Agent 系统的工程师来说，这篇论文提供的不只是一个自动化工具，更是一套低成本、高信息量的诊断方法论——而且它来自真实的生产环境，不是实验室里的 toy setting。
