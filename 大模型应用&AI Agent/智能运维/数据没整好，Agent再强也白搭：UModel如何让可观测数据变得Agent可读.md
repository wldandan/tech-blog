# 数据没整好，Agent再强也白搭：UModel如何让可观测数据变得Agent可读

LLM Agent做微服务故障诊断（根因分析，RCA）的论文越来越多，但有个前提很少被讨论：**Agent拿到的数据，它真的读得懂吗？**

生产环境的可观测数据分布在Prometheus、Elasticsearch、Jaeger、K8s API Server等五六套系统里。指标是一条裸数字，日志是一行裸文本，调用链是一串裸span。同一个服务在APM里叫 `payment`，在K8s里叫 `payment-7d4f8b9c6`，在云资源视图里叫 `i-bp1xxx`。Agent想查一个服务的CPU使用率，得先搞清楚：去哪套系统查、用哪种查询语言、查完了怎么把不同系统的数据拼起来。每套系统有自己的认证方式、分页逻辑、时间格式。

这不是推理问题，是数据基础设施问题。把最聪明的Agent扔进一个数据没整好的环境里，它大部分精力都花在"搞清楚数据在哪、怎么查"上，而不是"分析数据里有什么问题"。

来自同一个团队（中科院计算机网络信息中心 + 阿里云 + 清华 + 南开）的两篇论文，恰好构成了这个问题的完整解。第一篇提出了***UModel，把碎片化可观测数据统一成Agent能理解的对象模型***，在阿里云生产环境跑了一年多。第二篇是在UModel之上做的***Benchmark：数据干净了，评估才能做得细*** —— 不只判答案对不对，还判推理过程有没有依据。两篇共享同一套数据：**AIOps2025**和**RCA100**，合计**503个专家标注案例**，经过了**6000+支竞赛队伍**的实战验证。

###### PART 01
# 为什么Agent读不懂可观测数据

论文给出了四条"Agent-Ready数据模型"的标准，每条对应传统可观测栈在生产环境中反复暴露的一个硬伤。

![alt text](01_four_problems.png)

:::success
**数据没有语义。** 指标名叫 `node_cpu_seconds_total`，人类运维知道它是counter类型、单位是秒、需要套rate函数才能得到利用率。LLM Agent看到的只是一个token序列。Agent自己写PromQL查这个指标时，典型错误包括：给counter套了avg而非rate、rate里忘了时间范围、histogram用了错的分位数函数、不同单位的指标直接做除法。**再强的推理也补不上"不知道这个指标是counter还是gauge"的信息缺口。** 输入本身就缺了必要信息。

**指标、日志、调用链之间没有关系。** 它们各自存在不同系统里，没有任何东西告诉 Agent"这条曲线和那行日志来自同一个服务"。运维靠脑子里的架构图来关联："checkout服务延迟飙升，上游是frontend，下游是payment，payment又依赖Redis"。Agent没有这张图，能做的只是统计相关性，不是因果推理。

**只有数据，没有工具。** 可观测系统是只读仪表盘。Agent看到DiskFull告警，但没法执行绑定的清理脚本。反过来，Agent想从海量日志里提取信息，没有预处理管道，直接把GB级原始日志灌进上下文窗口，有用的错误信息可能被淹没在几十万条INFO日志里。

**每套系统有自己查询语言。** PromQL查指标（函数式嵌套语法），SQL或Elasticsearch DSL查日志，Jaeger gRPC API查调用链，K8s API查事件。Agent拼一个完整系统视图要同时学会五六种查询语言，每种语言的错误处理、超时策略、分页机制都不一样。花在"学会怎么查"上的token 步数，往往比"分析查出来的结果"还多。

这四个问题指向同一个结论：***Agent做不好故障诊断，有时候不是模型不够强，是数据太乱了。***
:::

###### PART 02
# UModel：三层架构填四个坑

UModel的思路是把所有可观测资产建模成统一的对象，然后在这些对象之间建立显式关系。整个系统分三层。

![alt text](02_image.png)


## 2.1 对象层：把"死数据"变成"活对象"

三类核心概念构成一张语义图：

:::success
- **EntitySet**：描述系统里有什么。服务、Pod、节点、DB 实例都是Entity。每个Entity自带领域知识：自然语言描述、诊断规则、甚至绑定的操作脚本（比如给DiskFull告警绑定cleanup.sh）。
- **EntitySetLink**：描述实体间的拓扑关系。link_type区分三类边：calls（A调用B）、contains（Namespace包含Service）、hosts（Node承载Pod）。边的两端通过显式的字段映射连接，不再是运维脑子里的隐含知识。
- **DataSet**：描述一个实体的观测数据长什么样。MetricSet定义指标的schema 和类型（counter/gauge/histogram），LogSet定义日志的字段映射，TraceSet定义调用链的trace_id和parent_span_id。DataLink把DataSet逻辑绑定到它的EntitySet上，StorageLink做物理路由到具体的存储引擎。
:::

关键效果是：每个对象自带语义元数据。Agent不再从裸指标名猜测怎么查，MetricSet标注了类型、单位、建议查询模板。关系也不再靠猜，EntitySetLink把服务间调用、Pod和Node部署关系都显式建模为图边。Agent沿图走就行：从报错的服务节点出发，沿calls边回溯上游，沿hosts边跳到物理节点检查基础设施。

:::success
## 2.2 查询层：别让Agent直接写PromQL

U-SPL是一种管道式查询语言，语法是Unix pipe风格：`source | command1 | command2 | ...`。包含三类查询：MetaSearch查schema定义，USearch搜具体实体实例（支持关键词搜索、属性过滤、模糊匹配、多因子排序），GSearch查拓扑关系（graph-match做图遍历，graph-call调用内置图算法或直接嵌入Cypher语句）。

和传统方式对比是最直观的。Agent想查某个服务的golden metrics（请求量、错误率、延迟），传统路径是：手动选project和metric store → 拼接 `promql_query_range`（含显式聚合、label 筛选、时间范围）→ 查询返回后手动reverse-map label → 算md5转entity_id。六七个步骤，每个都可能出错。同样的查询用U-SPL：`.entity_set('apm.service') | get_golden_metrics`。

但整个查询层最关键的设计不是U-SPL本身，而是UModel在它之上加的一层**data-agent**。data-agent把U-SPL封装成 `analyze_golden_metric(entity)`、`analyze_error_log(entity)` 这种领域专用工具。***主Agent（RCA Agent）决定"分析什么"**，**data-agent决定"怎么查、怎么执行、怎么压缩结果"***。这个分离解决了两个问题：主Agent不需要理解查询语法，幻觉率大幅下降；data-agent把几千个时序点压缩成结构化摘要，主Agent的上下文消耗降低了**80% 以上**。
:::

## 2.3 应用层：通过MCP暴露给Agent

UModel通过MCP（Model Context Protocol）Server向Agent暴露工具。PaaS层提供search_entity、get_topology、drill_down、get_golden_metrics等高层实体操作，IaaS层提供execute_promql、execute_spl等底层查询接口保留灵活性。MCP Server内部把Agent的自然语言意图翻译成U-SPL查询或底层API调用。

## 2.4 生产验证

UModel在阿里云生产环境运行超过一年。**数万workspace、数百云产品、数千标准化配置模型**，覆盖容器服务、APM、云基础设施监控等场景。跨异构系统（K8s、网络、数据库、中间件）统一了数千个EntitySet和EntitySetLink配置。**每秒数百万次实体和关系操作，千万级数据检索秒级响应。** 论文还提到，UModel内置了Metric Explorer等探索工具，支持异常检测、自动drill-down、时序聚类和根因定位。

###### PART 03
# 数据干净了，评估才能做细

有了UModel这样的基础设施，下一个问题自然就是：Agent在上面诊断的怎么样？这也是第二篇论文的核心。

## 3.1 为什么只看最终答案不够

现有RCA基准（RCAEval 735案例、OpenRCA 335案例）的做法很简单：给Agent一堆监控数据，它输出根因组件名称，和标注做字符串匹配，对上得分，对不上零分。

**这个逻辑有漏洞。** Agent可以靠关键词频率蒙对 —— 日志里哪个服务名出现最多就说谁是根因。它不需要真的跨模态比对：指标在告警时间点有没有同步异常？日志里的错误栈和调用链上的延迟节点是不是指向同一个下游？故障是先出现在上游然后传播到下游，还是反过来？这些问题现有基准都不考。

论文把评估拆成定位、识别、推理三个维度，然后通过两套互补的数据集落地。

![alt text](04_image-1.png)

## 3.2 两套数据集：AIOps2025和RCA100

两篇论文共享这两套数据集。它们不只是规模不同，底层系统、数据模态、标注形式都不一样：

| | AIOps2025 | RCA100 |
|--|-----------|--------|
| 案例数 | 400 | 103 |
| 底层系统 | HipsterShop（10微服务K8s） | OTel Demo Store（阿里云ACK） |
| 数据模态 | 3（指标+日志+调用链） | **6**（+ Events + Alerts + Topology） |
| 故障分类 | 9 大类 × 18 种 | **28种 × 6语义组** |
| Agent 输入 | 开放式自然语言异常描述 | 结构化告警事件 |
| 标注形式 | 平面关键证据列表 | 因果链（3-4步，含检查点） |
| 推理评分 | 可解释性 + 效率（互锁） | 因果链节点匹配 + 检查点击中 |
| 评估权重 | 定位 0.40 + 识别 0.40 + 推理 0.20 | 定位 0.40 + 识别 0.30 + 推理 0.30 |
| 数据布局 | 按天×小时分片（2835文件/11.9GB） | 每案例独立包（721文件/3.4GB） |

AIOps2025面向开放式告警工单场景。Agent拿到一段自然语言异常描述和一个时间窗口，自己决定加载哪些数据、分析哪些模态、从哪开始排查。标注形式是平面的关键证据列表，每个案例列出该模态下必须关注的指标名、日志关键字、调用链节点。标注成本低，适合大规模场景。

RCA100面向结构化告警场景。Agent从一个明确的告警事件出发（90/103 案例带单条告警实体），利用 6 种模态和显式拓扑图做诊断。标注形式是因果链，每个案例 3-4 步（cause → propagation → impact），链上挂了 **661 个检查点，99.5% 带数值约束**（比如 `error_count ≥ 8829` 且 `error_rate ≥ 0.50`）。标注成本高但信息量大，能看到证据怎么从根因经传播节点串到最终影响面。

## 3.3 三个评估维度的具体实现

![alt text](05_evaluation_dimensions.png)

:::success
**Localization（定位）。**  故障在哪个实体？AIOps2025对Pod级故障要求精确Pod标识符，网络攻击类例外（证据在两端都明显，命中源或目标即可），例如微服务里"服务名"和"Pod实例名"是完全不同的诊断粒度，Agent说是"emailservice服务"，等于没定位。RCA100采用UModel实体ID进行匹配，答对全分，拓扑相邻给部分分。

**Identification（识别）。** 什么类型的故障？CPU饱和、JVM GC还是网络丢包？每种对应完全不同的修复动作。AIOps2025采用两步匹配：先做关键词检测（命中ground-truth故障描述关键词即满分），未命中时，使用embedding相似度fallback。为防止Agent堆砌关键词刷分，reasoning字段只取前20个词参与匹配。RCA100则是严格的28类分类匹配。

**Reason（推理）。** 最有区分力的维度，两个数据集实现方式不同。
- **AIOps2025拆成两个互相制约的子维度**：可解释性（Explainability）既要覆盖足够多的关键证据点，又不能堆量刷覆盖率。效率（Efficiency）只在定位正确时计算，防止Agent靠模糊回答投机。注意，**只对定位正确的案例计算效率**，如果定位错了但推理很短，不会因为"短"而得高分。这两个子维度互相约束：你既要覆盖够多证据，又不能靠堆量来刷覆盖率。
- **RCA100用因果链 + 检查点**：每个案例标注了一条 3-4 步的因果链（cause → propagation → impact），每条链上总共挂了 **661个观测检查点，99.5%带数值约束**。Agent必须走对因果链节点（说出正确实体和传播路径），且每个节点上引用的观测数据命中检查点的数值约束。光说"error_count异常"不算分，数值也得对。
:::

两个数据集的权重分配反映了不同的侧重：AIOps2025定位和识别各占 0.40，推理占 0.20（可解释性 0.10 + 效率 0.10），因为开放式告警工单场景下，先把故障在哪和是什么搞清楚最重要。RCA100实体定位占 0.40，故障识别和推理过程各 0.30，因为结构化告警场景下因果链的正确性跟根因识别同等重要。

## 3.4 直接证据：UModel让同一Agent精度 +8%

论文做了一个关键实验：同一批AIOps2025数据，原始格式和UModel建模后，同一个naive Agent的根因定位精度**提升了8%**。Agent没变，数据组织变了。四个坑填上之后，数据有了语义不用猜、有了关系可以沿图遍历、有了工具可以先蒸馏后分析、有了统一接口不用学六种查询语言，推理能力才有了发挥空间。

## 3.5 标签怎么打的

每个故障场景被多次重复注入，三位SRE专家独立盲标（互不知道对方输出），资深专家裁定分歧。被丢弃的注入有三类：容错机制吞了、可观测足迹太薄连专家都追溯不了、实际表现和注入意图偏离（CPU 压力意外触发 OOM kill）。最终标签反映的是专家实际观察到的，不是注入参数。这也是为什么 400 次有效注入背后有大量被筛掉的注入记录。

**6000+支竞赛队伍验证。** AIOps2025是2025 CCF AIOps挑战赛赛题（**561支队伍、1068名选手**），RCA100是阿里云天池AI-Native编程挑战赛赛道（**5532 支队伍**）。6000+支队伍在同一个评估协议下提交评测，等于对评分公式的稳定性和反刷分设计做了大规模压力测试。

###### PART 04
# 总结

这两篇论文放在一起，补上了一个Agent故障诊断领域长期被跳过的环节：**Agent用的数据本身是不是好的。**

以前这是两组人的事。数据团队管存和查，Agent团队管训和评。但这两篇论文说明了一件事：Agent做不好诊断，有时候跟模型没关系。数据没有语义，Agent写查询就在犯错；数据没有关系，Agent只能统计相关不能因果推理；没有工具，Agent被原始数据淹掉；接口不统一，Agent精力全花在ETL上。

UModel给了这个方向一个跑过生产验证的架构参考：对象化建模让数据自描述，语义图让关系可遍历，U-SPL+data-agent让Agent不再直接面对查询语言的复杂性。Benchmark给了一个可信的评估框架：答案对≠推理对，答案错≠过程全错，定位、识别、推理三个维度拆开看才知道问题出在哪一步。

两者加起来，是**Agent在微服务故障诊断这个场景里从"能做"走向"可信"的基础**。
